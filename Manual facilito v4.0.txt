0. CÓMO TRABAJAR CON ESTE PROYECTO (MODO QUIRÚRGICO)
________________________________________

🎯 FILOSOFÍA

Este proyecto se edita con "modo quirúrgico": cambios pequeños,
verificables, reversibles, uno a la vez. NO se hacen cambios
masivos "por las dudas" ni refactors grandes sin medición.

La regla de oro es: si no lo medimos, no lo tocamos.

📋 PROTOCOLO DE EDICIÓN

Cada vez que se va a modificar código, se sigue este protocolo
estricto:

1. DIAGNÓSTICO PRIMERO (solo lectura)
   - Greps, wc -l, sed -n, lectura de archivos.
   - Nada de tocar hasta entender el problema.
   - Si hay dudas, se pregunta antes de asumir.

2. CAMBIOS QUIRÚRGICOS CON SELECCIÓN COMPLETA
   - La IA (o el dev) le dice al humano:
       "Seleccioná TODO este bloque (desde X hasta Y)."
       "Reemplazalo por este otro bloque completo."
   - NO se edita línea por línea en el medio.
   - NO se dice "borrá esta línea y agregá esto acá".
   - Siempre bloque completo, principio a fin.

   ¿Por qué? Porque reduce errores de sintaxis, evita que se
   pierdan líneas en el medio, y hace el cambio reversible: si
   algo sale mal, el bloque viejo era una unidad, no un
   fragmento.

3. BACKUP ANTES DE CADA CAMBIO ESTRUCTURAL
   - cp archivo archivo.bak-<nombre-fase>
   - Ejemplo: AdminSidebar.tsx.bak-fase1
   - Los backups se dejan hasta que el cambio está confirmado
     funcionando en producción.

4. UN CAMBIO, UN REBUILD, UNA VERIFICACIÓN
   - No se acumulan cambios sin rebuildear entre medio.
   - Rebuild → Ctrl+Shift+R → verificar → próximo cambio.
   - Si un cambio se siente "mucho mejor", se mide con
     React DevTools / Performance antes de seguir.

5. VERIFICACIÓN CON GREP DESPUÉS DEL CAMBIO
   - No se confía en "quedó bien" sin comprobar.
   - grep -n "<lo que cambió>" archivo
   - Se compara antes vs después.

6. Ctrl+Shift+R DESPUÉS DE CADA REBUILD
   - El navegador cachea chunks agresivamente.
   - Sin recarga forzada, se ven builds viejos y da
     falsos positivos/negativos.

🖋️ REGLAS DE ESTILO

- Cero emojis en la UI. Los emojis del código/comentarios
  internos pueden quedar.
- SVG heredados de lucide-react. No introducir librerías de
  íconos nuevas.
- Colores del tenant siempre (primary, secondary, etc.).
  Nunca hardcodear colores de marca.
- No crear archivos nuevos si se puede reusar lo existente.
  Antes de crear un archivo, grep.
- Nunca "te doy el archivo completo" salvo que sea un archivo
  NUEVO.
- Todo request autenticado del frontend usa apiFetch (no fetch
  directo).
- Todo logout usa performLogout (no localStorage.clear()).
- Todo error de auth es 401 (no 400, no 500).
- No romper la estética bajo ningún concepto. Si un cambio de
  performance afecta la estética, se pregunta antes de aplicarlo.

🎨 REGLA DE IMÁGENES (post-tienda)

- <Image> de Next solo funciona con URLs absolutas o archivos
  en public/.
- URLs relativas (/uploads/...) rompen <Image> con 400.
- En esos casos, usar <img> nativo.
- Esto se descubrió optimizando la tienda pública y se aplica
  a todo el proyecto.

🔒 REGLAS DE ORO DEL AUTH

1. NUNCA devolver password, totpSecret, failedLoginAttempts,
   lockedUntil, emailVerifiedAt, lastLoginAt, lastLoginIp al
   frontend. Usar toPublicUser().
2. NUNCA decodificar JWT con jwt.decode() en un controller.
   Usar req.user (ya validado por AuthGuard/JwtStrategy).
3. TODO logout debe llamar a performLogout() de
   lib/auth/logout.ts. NO usar localStorage.clear().
4. TODO request autenticado del frontend debe usar apiFetch()
   de lib/api.ts. NO usar fetch directo.
5. TODO error de auth debe ser 401, no 400 ni 500. Los 401
   activan el refresh automático.
6. NUNCA loguear tokens, passwords, ni secrets.
7. TODO cambio de password/reset/2FA-disable debe revocar
   todos los refresh tokens del user.
8. NUNCA rotar JWT_SECRET sin doble validación (_NEW + _OLD)
   y ventana de 15 min.
9. TODO nuevo endpoint autenticado debe estar en
   AuthMiddleware.forRoutes o tener
   @UseGuards(AuthGuard('jwt')).
10. TODA acción sensible (login, reset, 2FA, cambio de rol)
    debe quedar registrada en auth_events.
11. Usar isBuyer(), isDriver(), isProfessional() de
    lib/roles.ts para condicionar acciones por rol.
12. El nombre del evento de logout es authChange (SIN "d").
    No confundir con authChanged.

🛑 LO QUE NO SE TOCA SIN RAZÓN

- /etc/nginx/sites-available/facilito
- /opt/facilito/apps/frontend/next.config.ts
- /opt/facilito/apps/frontend/.env.local
- /opt/facilito/apps/frontend/package.json
- /etc/systemd/system/facilito-frontend.service*
- /opt/facilito/apps/backend/.env

Si hay que tocar alguno de estos, se avisa explícitamente y se
justifica por qué.

2. LOS COMANDOS PRINCIPALES
________________________________________

🟢 Comando 1: Rebuild frontend

  /opt/facilito/rebuild.sh

Qué hace:
  1. Para el servicio facilito-frontend
  2. Mata procesos zombie en puerto 3001
  3. Borra .next (build viejo)
  4. Rebuild con Webpack (~25-30s)
  5. Verifica que el .next/BUILD_ID exista
  6. Arranca el servicio
  7. Healthcheck con reintentos (8 intentos, 1s cada uno)
  8. Muestra: puerto escuchando, chunks sirviendo vs disco, Build ID
  9. Imprime bloque de "📋 COMANDOS ÚTILES"

Cuándo usarlo:
  - Editaste algún archivo .tsx, .ts, .js, .css del frontend
  - Cambiaste algo en next.config.ts
  - Cambiaste algo en package.json
  - El frontend se ve raro / no carga

Tiempo: ~40 segundos.
Después: Ctrl+Shift+R en el navegador.

________________________________________
🟢 Comando 2: Rebuild backend

  /opt/facilito/rebuild-backend.sh

Qué hace:
  1. Para el servicio facilito-backend
  2. Mata procesos zombie en puerto 3000
  3. Borra dist/ (build viejo)
  4. Rebuild con Nest (pnpm run build)
  5. Verifica que dist/main.js exista
  6. Arranca el servicio
  7. Healthcheck con reintentos (8 intentos, 1s cada uno)
  8. Muestra: puerto escuchando, dist/main.js en disco
  9. Imprime bloque de "📋 COMANDOS ÚTILES"

Cuándo usarlo:
  - Editaste cualquier archivo .ts en apps/backend/src/
  - Cambiaste algo en .env del backend
  - Tocaste módulos de auth, DB, controllers, services
  - El backend devuelve 500 o no responde

Tiempo: ~30 segundos.

________________________________________
🟡 Comando 3: Cambiar de IP

PASO 1 — Averiguar la IP actual:
  hostname -I

PASO 2 — Cambiar la IP:
  /opt/facilito/cambiar-ip.sh <NUEVA_IP>

Qué hace:
  1. Regenera el cert SSL con la nueva IP en el SAN
  2. Verifica que nginx tenga server_name _; (lo corrige si no)
  3. Verifica que .env.local tenga NEXT_PUBLIC_API_URL=/api
  4. Para el frontend, mata zombies, lo reinicia limpio
  5. Muestra resumen: SAN del cert, puerto 3001, test HTTPS

Cuándo usarlo:
  - Moviste el servidor de red/WiFi
  - La IP del servidor cambió
  - Vas a hacer una demo en otra red

Tiempo: ~15 segundos.

PASO 3 — Abrir el navegador:
  https://<NUEVA_IP>/

⚠️ NO toca:
  - La base de datos (URLs relativas)
  - .env.local (ya es relativo)
  - next.config.ts (acepta cualquier host)
  - El código del frontend

________________________________________
🔴 Comando 4: Reiniciar servicio (sin rebuild)

  # Frontend:
  systemctl restart facilito-frontend.service

  # Backend:
  systemctl restart facilito-backend.service

O con los scripts nuevos (recomendado):
  rf    # restart frontend con healthcheck
  rb    # restart backend con healthcheck

Qué hace: solo reinicia el servicio, sin tocar el build.

Cuándo usarlo:
  - El servicio se colgó pero NO cambiaste código
  - Querés reiniciar rápido sin rebuild

Tiempo: ~5 segundos.

🔄 ROTACIÓN DE JWT_SECRET

Cuándo rotar:
  - Sospecha de filtración
  - Cada 6-12 meses por política
  - Cuando un dev con acceso se va del equipo

Procedimiento (sin cortar sesiones):
  # 1. Generar nuevo (96 hex)
  node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

  # 2. Editar .env del backend:
  #    JWT_SECRET_NEW=<nuevo>
  #    JWT_SECRET_OLD=<el-actual>
  #    OJO: durante la rotación, JWT_SECRET no debe existir

  # 3. Rebuild + restart backend
  /opt/facilito/rebuild-backend.sh

  # 4. Verificar doble validación (token nuevo y viejo → 200)

  # 5. Esperar 15 min (vida del access token)

  # 6. Consolidar: JWT_SECRET=<el-nuevo>, borrar _NEW y _OLD

  # 7. Rebuild + restart
  /opt/facilito/rebuild-backend.sh

5. BASE DE DATOS
________________________________________

🗄️ TABLAS PRINCIPALES

users (campos de auth):
  - id, email, password (bcrypt, 10 rounds)
  - emailVerified, emailVerifiedAt
  - failedLoginAttempts, lockedUntil
  - lastLoginAt, lastLoginIp
  - totpSecret (AES-256-GCM), totpEnabled

refresh_tokens:
  - id, userId, tokenHash (SHA-256), expiresAt (30d)
  - revokedAt, replacedByTokenId (rotación)
  - lastUsedAt, ip, userAgent, createdAt

auth_events:
  - id, userId (nullable), eventType, ip, userAgent,
    metadata (jsonb), createdAt

password_resets: id, userId, tokenHash, expiresAt (15 min),
  usedAt, ip, userAgent, createdAt

email_verifications: igual pero expiresAt (24 h)

backup_codes: id, userId, codeHash (SHA-256), usedAt, createdAt

Eventos registrados en auth_events:
  login_success, login_failed, logout,
  password_reset_requested, password_reset_completed,
  password_changed, email_verified,
  refresh_token_used, refresh_token_revoked,
  2fa_enabled, 2fa_disabled, 2fa_verified, account_locked,
  order_delivery_updated_after_completion,
  order_local_delivery_updated_after_completion.

💾 BACKUP Y RESTAURACIÓN

Con scripts (recomendado):
  bkdb              # solo la DB
  bkfull            # DB + apps + nginx

Manualmente:
  mkdir -p /opt/facilito/backups

  docker exec facilito_postgres pg_dump -U facilito_admin facilito_db \
    > /opt/facilito/backups/db_$(date +%Y%m%d_%H%M%S).sql

  tar -czf /opt/facilito/backups/apps_$(date +%Y%m%d_%H%M%S).tar.gz \
    --exclude='node_modules' --exclude='.next' --exclude='dist' \
    /opt/facilito/apps

  cp -r /etc/nginx/sites-available \
    /opt/facilito/backups/nginx_$(date +%Y%m%d_%H%M%S)

Restaurar DB:
  docker exec -i facilito_postgres psql -U facilito_admin facilito_db \
    < /opt/facilito/backups/db_YYYYMMDD_HHMMSS.sql

Restaurar código:
  tar -xzf /opt/facilito/backups/apps_YYYYMMDD_HHMMSS.tar.gz -C /

Consultar con script:
  q "SELECT COUNT(*) FROM users;"
  q "SELECT slug, name FROM tenants LIMIT 5;"

Abrir psql interactivo:
  db
  # dentro: \dt (tablas), \d tabla (estructura), \q (salir)

🚀 ESCENARIO A: Demo a inversionistas (mover a otra red)

11. REDISEÑO UCP — FULFILLMENT Y COBRO A DESTINO
________________________________________

📅 Fecha de implementación: 10/10/2026
🎯 Objetivo: normalizar el modelo de entrega al estándar UCP
📊 Fases: 7 (backend, frontend, DB, migración)

📌 VALORES CANÓNICOS DE FULFILLMENT

| Valor    | Significado                     | Cuándo se usa                          |
|----------|---------------------------------|----------------------------------------|
| pickup   | Retiro en tienda                | El comprador retira                    |
| shipping | Encomienda (MRW, Zoom, etc.)    | El comprador paga al recibir o adelantado |
| delivery | Delivery local (facilito)       | Legacy + delivery propio               |

⚠️ delivery es legacy. El estándar UCP solo reconoce pickup y shipping.

📦 ESTRUCTURA DE paymentMetadata

{
  "fulfillment": "pickup" | "shipping" | "delivery",
  "delivery": {                     // solo si fulfillment === 'shipping'
    "company": "mrw",
    "companyName": "MRW",
    "costUsd": 12 | null,           // null = cobro a destino
    "costVes": 2400 | null,
    "selected": true,
    "estimatedDays": "2-3 días hábiles",
    "trackingNumber": null,
    "address": "...",
    "payOnDelivery": false          // ← NUEVO
  },
  "localDelivery": {                // solo si fulfillment === 'delivery'
    "fee": 2,
    "distanceKm": 1.5,
    "etaMinutes": 15
  }
}

🎯 REGLA DE COHERENCIA

- pickup → NO puede tener delivery.company (BadRequestException).
- shipping → SÍ debe tener delivery.company.
- delivery → SÍ debe tener localDelivery.

💰 COBRO A DESTINO

Cuando el admin activa "Cobro a destino" para una empresa en
DeliverySettings:
  - costsUSD[company] = null.
  - paymentMetadata.delivery.costUsd = null.
  - NO se suma al totalAmount (el comprador paga al recibir).
  - Los modales muestran badge "Cobro a destino" en ámbar.

📊 ESTADO DE LA DB POST-MIGRACIÓN

  docker exec -i facilito_postgres psql -U facilito_admin -d facilito_db -c "
  SELECT
    \"paymentMetadata\"->>'fulfillment' AS fulfillment,
    CASE WHEN \"paymentMetadata\"->'delivery'->>'company' IS NOT NULL
         THEN 'con_company' ELSE 'sin_company' END AS delivery_state,
    COUNT(*)
  FROM orders
  GROUP BY 1, 2
  ORDER BY 1, 2;"

Distribución esperada (post-migración):
  fulfillment | delivery_state | count
  ------------+----------------+-------
  delivery    | sin_company    |     4
  pickup      | sin_company    |    16
  shipping    | con_company    |     6+

🚨 REGLAS DE NEGOCIO

1. Un repartidor NO puede comprar. El backend valida
   role !== 'repartidor' al crear orden.
2. Un profesional NO puede comprar.
3. El kiosco es autoservicio presencial → NO permite encomienda.
   Solo pickup + delivery local.
4. El fulfillment es la fuente de verdad. Se calcula en create()
   y en updateDelivery().
5. costUsd: null = cobro a destino (no es error, no se suma al total).
6. El updateDelivery fuerza fulfillment='shipping' al agregar
   delivery.company.
7. tenantId es obligatorio al crear orden (400 si falta).

           role === 'admin' || role === 'owner';

    const role = (user.role || user.activeRole || '').toLowerCase();
    return role === 'profesional' || role === 'professional';
  }

📁 UBICACIÓN

  components/ui/SearchableDropdown.tsx

📝 API

```typescript
interface SearchableDropdownOption {
  value: string;
  label: string;
}

interface SearchableDropdownProps {
  // Obligatorios
  value: string;
  onChange: (value: string) => void;  // recibe STRING, no event
  options: SearchableDropdownOption[];

  // Tema (obligatorios salvo secondary y borderColor)
  primary: string;        // color del tenant (hex o var(--...))

11. FASE K — CANALES DE VENTA (KIOSK/ONLINE)
________________________________________

📅 Fecha de implementación: 19/10/2026
🎯 Objetivo: separar los flujos de kiosco (POS presencial) y tienda online.
   Cada producto/servicio puede estar disponible en uno, en otro, o en ambos.
   El kiosco y la tienda comparten catálogo pero filtran por canal.

📌 MODELO DE DATOS

Productos (tabla products):
  - availableKiosk BOOLEAN DEFAULT true
  - availableOnline BOOLEAN DEFAULT true

Servicios (tabla services):
  - availableKiosk BOOLEAN DEFAULT true
  - availableOnline BOOLEAN DEFAULT true
  - serviceModality sigue siendo descriptivo (Presencial / A Domicilio / Online / Híbrido)

Reglas de canal:
  Kiosk acepta: productos con availableKiosk=true y servicios con availableKiosk=true
  Kiosk RECHAZA (defensa en profundidad): servicios con serviceModality='A Domicilio' o 'Online / Virtual'
  Tienda online acepta: productos con availableOnline=true y servicios con availableOnline=true

🎨 UI ADMIN

  - Form crear/editar producto → 2 toggles: "Disponible en kiosco" + "Disponible en tienda online"
  - Form crear/editar servicio → 2 toggles idénticos
  - Tabla productos/servicios → columna "Canales" con badges K (kiosco) y W (online)
  - Header admin → al activar kiosco, valida que haya ≥1 item disponible.
    Si no → toast de error y no se activa.

🔒 VALIDACIONES BACKEND

  createOrder:
    - si source='kiosk' y algún item tiene availableKiosk=false → 400
    - si source='kiosk' y algún servicio tiene serviceModality='A Domicilio'/'Online / Virtual' → 400
    - si source='kiosk' → fulfillment forzado a 'pickup'

  createBooking:
    - si source='kiosk' y serviceModality in ('A Domicilio', 'Online / Virtual') → 400

⚠️ LECCIONES APRENDIDAS DURANTE K

1. **`dist/` vs proceso vivo.** Cuando el código cambia pero el comportamiento
   no, verificar `ps -eo pid,lstart | grep node` vs `ls -la dist/...js`. Si
   el proceso es anterior al dist, hace falta rebuild completo.

2. **Scripts Node con regex multilínea son frágiles.** Para insertar líneas
   en posiciones específicas, `sed -i '<num>a\...'` es más robusto. Y siempre
   verificar con `sed -n '<ini>,<fin>p'` antes de tocar.

3. **`source.ts` puede tener indentación distinta a la esperada.** Usar
   `sed -n` para ver la zona antes de tocar, nunca "buscar y reemplazar" a ciegas.

4. **Productos con tenantId inconsistente.** El path de imágenes (`/uploads/<tenantId>/...`)
   puede no coincidir con el `tenantId` de la fila. Verificar con:
   q "SELECT id, name, \"tenantId\", \"mediaUrls\"[1] FROM products WHERE \"mediaUrls\"[1] IS NOT NULL AND \"mediaUrls\"[1] NOT LIKE '%' || \"tenantId\" || '%';"
